# Copysinger PRD

- **상태**: Baseline 확장
- **버전**: 0.6
- **작성일**: 2026-08-05
- **제품 범위**: Next.js 앱 + PostgreSQL + Modal CPU 분석 서비스 + Modal SoulX-Singer API

## 제품 개요

Copysinger는 Google 계정으로 로그인한 사용자의 테스트 가창을 분석해 보컬 프로필을 만들고, 노래별 보컬 프로필과 비교하여 원키 적합도와 추천 노래방 키를 계산한다. 최종적으로 100곡 전체를 적합도 순으로 제시하고, 사용자가 티켓을 사용해 선택한 곡에만 기존 SoulX-Singer SVC 기능으로 사용자 목소리 합성 데모를 제공한다. 보컬 프로필의 레퍼런스 오디오와 합성 결과는 Leemage에 저장하며, 믹싱은 재접속 후에도 상태와 결과를 확인할 수 있는 영속 큐로 처리한다.

## 핵심 사용자 흐름

```text
Google OAuth 로그인
  → 사용자 테스트 녹음
  → 사용자 보컬 프로필 생성
  → 노래 보컬 프로필과 비교
  → 원키 적합도 / 추천 노래방 키 계산
  → 전체 곡 적합도 순위 + 추천 이유 출력
  → 티켓 1개로 선택한 곡의 사용자 목소리 합성 데모
  → 믹싱 히스토리에서 상태와 결과 확인
```

합성 데모는 현재 구현·검증된 기반 기능이다. 다음 구현은 데이터 기반 → 사용자 프로필 → 곡 카탈로그 → 적합도 계산 → 추천 결과 순서로 진행한다.

## 목표

- 짧은 테스트 가창만으로 설명 가능한 보컬 프로필을 생성한다.
- 사용자와 곡의 음역·테시투라를 동일한 분석 버전으로 비교한다.
- 곡별 원키 적합도와 정수 단위 추천 키 이동 값을 제공한다.
- 100곡 카탈로그 전체를 적합도 순으로 정렬하고 사람이 이해할 수 있는 추천 이유를 제공한다.
- 사용자가 명시적으로 선택한 추천 곡을 사용자의 목소리로 변환해 결과를 미리 들려준다.
- 사용자별 보컬 프로필, 티켓 원장과 믹싱 이력을 안전하게 분리해 관리한다.
- 장시간 믹싱을 서버 재시작과 브라우저 이탈에 영향받지 않는 백그라운드 작업으로 처리한다.
- 로컬 Docker PostgreSQL과 Prisma로 데이터 구조를 재현 가능하게 관리한다.

## 제외 범위

- 티켓 구매·결제·구독 기능
- Google 이외의 로그인 공급자와 이메일/비밀번호 로그인
- 상업 음원 제공 또는 저작권 라이선스 대행
- 발성 건강에 대한 의료적 진단
- 절대적인 가창력 순위 또는 성별·나이 추정
- 노래 100곡의 실제 데이터 입력: 목록은 추후 사용자 제공
- 실시간 스트리밍 변환

## 사용자 스토리

- **PRD-US-001**: 사용자는 브라우저에서 안내된 테스트 구간을 녹음하거나 파일로 제출할 수 있다.
- **PRD-US-002**: 사용자는 자신의 관측 음역, 주요 음역, 중심 음과 유효 음성 구간을 음악 용어를 이해하기 쉬운 표기로 확인할 수 있다.
- **PRD-US-003**: 사용자는 각 노래가 원키에서 얼마나 잘 맞는지 확인할 수 있다.
- **PRD-US-004**: 사용자는 노래방에서 적용할 추천 키 이동 값을 반음 단위로 확인할 수 있다.
- **PRD-US-005**: 사용자는 100곡 전체를 잘 어울리는 순서부터 낮은 순서까지 확인하고 각 곡의 추천 이유를 비교할 수 있다.
- **PRD-US-006**: 사용자는 선택한 노래를 자신의 목소리로 변환한 데모를 재생할 수 있다.
- **PRD-US-007**: 사용자는 추천 목록에서 원하는 곡의 `AI 믹싱`을 직접 시작하고, 자신의 테스트 녹음을 사용한 합성 진행 상태와 완료 결과를 해당 목록 항목에서 확인할 수 있다.
- **PRD-US-008**: 사용자는 분석된 관측 음역·주요 음역·음정 분포·시간별 피치 흐름과 유효 음성 구간을 한 화면에서 시각적으로 확인할 수 있으며, 내부 품질 진단 수치인 클리핑·RMS·샘플레이트는 성공 결과의 핵심 정보로 노출되지 않는다.
- **PRD-US-009**: 사용자는 60초보다 긴 파일을 선택했을 때 안내를 받고, 동의하면 첫 유효 음성부터 60초 구간으로 자동 정리해 분석할 수 있다.
- **PRD-US-010**: 사용자는 Google 계정으로 로그인하고 자신의 보컬 프로필, 추천과 믹싱 데이터만 조회·사용할 수 있다.
- **PRD-US-011**: 신규 사용자는 티켓 1개를 받고, AI 믹싱 요청 시 티켓 1개가 차감되는 사실과 현재 잔액을 확인할 수 있다.
- **PRD-US-012**: 사용자는 마이 페이지에서 지급·사용·환불·관리자 조정이 포함된 티켓 사용 내역을 확인할 수 있다.
- **PRD-US-013**: 사용자는 브라우저를 닫거나 나중에 다시 접속해도 믹싱 히스토리에서 대기·진행·완료·실패 상태와 완료 결과를 확인할 수 있다.
- **PRD-US-014**: 관리자는 허용된 계정으로 관리자 페이지에 접근해 사용자, 티켓 원장과 믹싱 작업의 운영 상태를 확인하고 사유를 남겨 티켓을 조정할 수 있다.
- **PRD-US-015**: 사용자는 재접속 후에도 자신의 보컬 프로필 목록과 상세 분석을 확인하고, 프로필 생성에 제출한 레퍼런스 보컬을 다시 들을 수 있다.
- **PRD-US-016**: 사용자는 최대 60초의 테스트 녹음 중 자신의 입력 파형을 실시간으로 보면서 마이크가 정상 동작하는지 확인할 수 있다.
- **PRD-US-017**: 사용자는 프로젝트의 녹음·업로드·합성 결과를 동일한 파형 플레이어에서 재생하고 파형을 눌러 원하는 위치로 이동할 수 있다.
- **PRD-US-018**: 사용자는 최대 60초의 제출 음성으로 기존처럼 저음·중음·고음 대표 구간과 전체 보컬 프로필 분석을 확인하면서, AI 믹싱에는 내부 무음과 품질이 낮은 구간을 제외한 중음 중심의 유성 phrase만 이어 붙인 별도 reference가 사용되도록 할 수 있다. 품질 좋은 중음 구간이 30초보다 짧으면 반복·padding 없이 실제 확보된 길이만 사용한다.
- **PRD-US-019**: 방문자는 로그인 전에 Copysinger가 음성 분석, 노래 추천과 AI 믹싱 데모를 어떻게 제공하는지 이해하고 Google 로그인 또는 음성 스캔으로 이동할 수 있다.
- **PRD-US-020**: 사용자는 마이크 권한, 녹음, 업로드, 분석 대기와 실패 상태를 하나의 명확한 음성 스캔 흐름에서 확인할 수 있다.
- **PRD-US-021**: 사용자는 보컬 프로필의 핵심 요약을 먼저 이해하고 필요할 때 음정 분포와 피치 흐름의 상세 근거를 확인할 수 있으며, 서양 음이름과 옥타브 표기는 한국어 계이름 및 짧은 용어 설명과 함께 이해할 수 있다.
- **PRD-US-022**: 사용자는 전체 추천을 검색·정렬·필터링하고, 선택한 곡의 실제 적합도 근거와 추천 키를 별도 상세 화면에서 확인할 수 있다.
- **PRD-US-023**: 사용자는 AI 믹싱의 실제 작업 상태를 이해하고, 라이브러리에서 과거 보컬 프로필과 믹싱 결과를 다시 찾아 재생·다운로드하거나 상세 내용을 확인할 수 있다.
- **PRD-US-024**: 사용자는 데스크톱, 태블릿과 모바일에서 일관된 내비게이션과 로딩·빈 상태·오류·비활성 상태를 접하고 키보드와 보조 기술로 핵심 동작을 수행할 수 있다.
- **PRD-US-025**: 사용자는 생성 순서를 반영한 이름과 서로 구분되는 커버로 보컬 프로필을 식별하고, 필요하면 이름을 직접 변경할 수 있다.
- **PRD-US-026**: 사용자는 추천 목록과 곡 상세에서 추천의 근거가 된 원본 YouTube 영상을 페이지를 벗어나지 않고 재생할 수 있다.
- **PRD-US-027**: 사용자는 다른 화면을 보고 있거나 나중에 다시 접속해도 티켓 지급, 보컬 프로필 분석과 AI 믹싱의 완료·최종 실패를 헤더 알림과 알림 이력에서 확인하고 관련 화면으로 이동할 수 있다.
- **PRD-US-028**: 관리자는 관리자 화면에서 곡과 영상 출처를 등록·교체하고 분석 및 믹싱 target 준비 상태를 확인·재시도한 뒤 준비된 곡만 추천 카탈로그에 공개할 수 있다.
- **PRD-US-029**: 관리자는 관리자 화면에서 자신의 보컬 프로필을 선택하고 업로드한 임시 음원을 사용해 커스텀 AI 믹싱을 실행한 뒤 결과를 재생하거나 다운로드할 수 있다.

## 기능 요구사항

### 녹음과 보컬 프로필

- **PRD-FR-001**: 웹 앱은 테스트 녹음 시작·정지·재녹음·미리 듣기와 파일 업로드를 제공해야 한다.
- **PRD-FR-002**: 분석 전 무음, 너무 짧은 입력, 과도한 클리핑, 낮은 voiced ratio를 검증해야 한다.
- **PRD-FR-003**: 사용자 보컬 프로필은 최소한 유효 최저/최고음, 10·50·90 분위 MIDI, 테시투라, voiced ratio, pitch stability를 포함해야 한다.
- **PRD-FR-004**: 프로필은 분석 알고리즘 버전과 원본 녹음 참조를 함께 저장해야 한다.
- **PRD-FR-021**: 보컬 프로필 결과 UI는 관측 음역·주요 음역·중심 음·유효 음성 구간, 음정별 상대 빈도와 다운샘플링된 시간별 피치 흐름을 반응형으로 표시해야 한다. `min/max`는 2·98 분위 관측 경계, 주요 음역은 p10·p90임을 제품 용어에서 과장하지 않아야 하며, 성공 결과에서 클리핑·RMS·샘플레이트와 raw MIDI 수치를 핵심 카드로 노출하지 않는다. 사용자-facing 분석 용어 설명에서도 MIDI를 별도 개념으로 소개하지 않는다.
- **PRD-FR-022**: 웹 앱은 업로드 파일 길이가 60초를 초과하면 자동 자르기 확인 대화상자를 표시하고, 사용자가 동의한 경우 최초 유효 음성부터 최대 60초의 표준 오디오를 분석·보관해야 한다.
- **PRD-FR-039**: 웹 앱은 로그인 사용자의 보컬 프로필 목록과 상세 시각화를 재접속 후에도 제공하고, 제출한 레퍼런스 보컬은 소유권을 검증하고 저장소 URL을 숨기는 Range 지원 웹 API를 통해 본인에게만 재생해야 한다.
- **PRD-FR-040**: 테스트 녹음 UI는 녹음과 동일한 마이크 스트림에서 실시간 파형과 경과 시간을 표시하고 60초 자동 종료, 수동 정지, 취소와 자원 정리를 지원해야 한다.
- **PRD-FR-041**: 웹 앱의 사용자 재생 가능한 오디오는 WaveSurfer 기반 공통 플레이어를 사용해 파형, 재생·일시정지, 탐색, 현재·전체 시간과 오류 fallback을 제공해야 하며 Blob URL과 소유권 검증 Range API를 모두 지원해야 한다.
- **PRD-FR-042**: 프로필 분석은 녹음·업로드 모두 최초 유효 음성부터 최대 60초의 시간 순서와 자연 분포를 보존한 표준 오디오를 사용하고, 사용자에게 보여주는 저음·중음·고음 대표 분석 구간과 기존 프로필 시각화도 유지해야 한다. AI 믹싱 reference는 같은 분석 소스에서 내부 무음·클리핑·저품질 구간을 제외한 **중음 영역의 유성 phrase만** 선택해 최대 30초의 별도 versioned artifact로 만들어야 한다. 선택된 중음 phrase는 원본 시간 순서를 유지하고 짧은 crossfade로 연결하며, 30초를 채우기 위해 저음·고음 구간을 섞거나 반복·padding하지 않는다. 품질 좋은 중음 구간이 30초보다 짧으면 실제 확보된 길이만 사용한다. 사람에게 보여주는 3-band 분석 구간 descriptor와 모델에 전달되는 mid-only synthesis reference descriptor를 분리하고, 새 계약의 중음 reference가 준비되지 않은 프로필은 AI 믹싱에서 전체 source로 조용히 대체하지 않아야 한다.
- **PRD-FR-043**: 음역 프로필, 음정 분포와 시간별 피치 추적은 shadcn Chart의 `ChartContainer`와 Recharts 기반 컴포넌트로 표시하고 반응형 크기, tooltip, null pitch gap, 키보드·스크린리더 접근성을 지원해야 한다.

### 곡 카탈로그와 분석

- **PRD-FR-005**: 곡, 출처 revision, 분석 revision과 카탈로그 소속은 PostgreSQL을 런타임 SSOT로 관리해야 한다. 곡 분석 결과는 사용한 출처와 pipeline contract를 추적할 수 있어야 하며, DB 이동이 필요할 때는 관리자 전용 JSON snapshot export/import를 사용한다. 저장소의 카탈로그 JSON artifact는 runtime·초기화 입력으로 사용하지 않는다.
- **PRD-FR-006**: 곡 보컬 프로필은 사용자 프로필과 같은 pitch 통계 단위와 분석 버전을 사용해야 한다.
- **PRD-FR-007**: 초기·운영 카탈로그는 관리자 음원 관리 화면에서 등록·분석·공개할 수 있어야 하며, DB 교체 시 현재 분석 결과와 외부 target metadata를 관리자 snapshot으로 반복 복원할 수 있어야 한다. 카탈로그 row가 아직 없는 빈 DB에서도 관리자 음원 관리 화면과 최초 snapshot 가져오기 action은 접근 가능해야 하며, 가져오기가 카탈로그를 생성할 때까지 기존 카탈로그를 요구하는 추가·검색·내보내기 action은 실행되지 않아야 한다. 이후 관리자 변경은 애플리케이션 재배포나 저장소 JSON 수정을 요구하지 않아야 한다.
- **PRD-FR-059**: 관리자 곡 관리는 서버 관리자 권한을 검증하고 제목·아티스트·정규화된 YouTube 출처와 target audio를 등록할 수 있어야 한다. UI는 내부 `target` 용어 대신 YouTube 영상이 사용자 미리듣기와 출처 식별에 쓰이고, 보컬과 반주가 함께 있는 원곡 파일 하나가 보컬 분리 후 곡 음역 분석·전체 원곡 기반 원키 추정·AI 믹싱에 쓰인다는 역할을 명확히 설명해야 한다. 관리자 target audio 업로드와 보컬 분석 업로드는 동일한 오디오 포맷(`wav`, `mp3`, `m4a`, `webm`)만 지원하고 FLAC은 지원하지 않으며, 모든 관련 파일 선택 UI는 지원 확장자를 선택 전에 명시적으로 보여줘야 한다. video ID와 원키는 URL·분석 결과에서 파생하며, 신규 또는 교체 출처는 URL과 대응 원곡 파일 하나를 함께 받는 별도 revision과 분석 작업으로 처리하고, 분석과 target이 모두 준비되기 전에는 추천에 공개하지 않으며 실패 원인과 제한된 재시도 동작을 제공해야 한다. 정상 상태에서는 별도의 두 번째 파일 입력을 노출하지 않고 원곡 파일 저장 복구가 필요할 때만 재업로드 action을 제공한다. 관리자는 공개 곡을 보관해 추천에서 제외하되 자료와 기존 믹싱 이력을 유지하고, 준비 완료 revision으로 다시 공개할 수 있어야 한다. 곡 aggregate의 영구 삭제 기능은 제공하지 않는다. 관리자는 같은 화면에서 카탈로그 snapshot을 export/import할 수 있어야 한다.

### 적합도와 추천

- **PRD-FR-008**: 키 적합도는 사용자의 이번 녹음에서 관찰된 주요 음역과 곡의 주요 음역 사이의 대칭적 겹침, 주요 음역 초과 부담과 관측 극단음 초과 부담을 반영하며 음역이 좁다는 이유만으로 최대 겹침 점수를 주지 않아야 한다. 보컬 분석 신뢰도는 모든 곡에 동일하게 더해지는 적합도 점수 항목으로 사용하지 않고 별도 안내 신호로 유지한다.
- **PRD-FR-009**: 추천 키는 허용 범위 안의 정수 semitone 후보를 평가해 최고 점수의 이동 값을 선택해야 한다.
- **PRD-FR-010**: 추천 결과는 동일 revision 입력에 대해 결정적이어야 한다. 응답과 영속 믹싱 작업은 사용한 보컬 프로필, 카탈로그 revision, 곡 분석 revision과 scoring algorithm version을 식별할 수 있어야 한다.
- **PRD-FR-011**: 추천 API는 원키 점수, 조정 후 점수와 키 이동 부담을 함께 반영한 단일 `추천 점수`로 카탈로그 전체를 결정적으로 정렬하며, 모든 곡의 원키 점수, 조정 후 점수, 추천 키, 추천 점수와 구조화된 이유 코드를 반환해야 한다. 사용자-facing 기본 정렬과 표시 순위는 같은 추천 점수를 기준으로 해야 한다.
- **PRD-FR-012**: UI는 이유 코드를 자연어 설명으로 표시하고 과도한 정확성을 암시하지 않아야 한다.

### 합성 데모 — 구현 완료 기반

- **PRD-FR-013**: 웹 앱은 레퍼런스와 타겟 오디오, SVC advanced settings를 Modal API로 전달해야 한다.
- **PRD-FR-014**: 변환 요청은 `queued → processing → succeeded | failed` 상태를 제공해야 한다.
- **PRD-FR-015**: 사용자는 완료된 결과 WAV를 재생·다운로드하고 작업을 취소·삭제할 수 있어야 한다.
- **PRD-FR-016**: 추천 실행 생성만으로 합성 작업을 자동 시작하지 않아야 하며, 사용자가 목록 항목의 `AI 믹싱`을 누른 곡만 사용자 보컬 프로필의 원본 테스트 녹음을 reference로 합성해야 한다.
- **PRD-FR-017**: 추천 목록 항목은 합성 전 `AI 믹싱` 버튼을 제공하고, 시작 후 `preparing → queued → processing → succeeded | failed` 상태와 “믹싱 중이에요” 안내를 표시하며 성공 시 결과 오디오 재생·다운로드를 제공해야 한다.
- **PRD-FR-018**: 추천 목록 합성은 `prompt_vocal_separation=false`, `target_vocal_separation=true`, `auto_pitch_shift=true`, `auto_mix_accompaniment=true`, `pitch_shift=0`의 고정 제품 preset을 사용하고 자동 피치 이동이 적용되는 AI 믹싱임을 명시해야 한다.
- **PRD-FR-019**: 운영자가 사용 권한을 확보한 카탈로그 target 오디오는 Git 비추적 local staging에서 catalog identity를 검증한 뒤 지원되는 원본 오디오 bytes/MIME을 유지해 Leemage에 사전 업로드하고 Song에 연결해야 한다. AI 믹싱은 작업 시점의 외부 URL 다운로드 대신 해당 READY target asset을 snapshot해 사용하며, SoulX가 합성 시작 시 내부 정규화를 수행한다. target이 준비되지 않은 곡은 티켓 차감 전에 믹싱을 거부해야 한다.
- **PRD-FR-020**: 기존 자유 reference/target과 advanced settings Workbench는 자동 추천 합성과 분리된 개발·진단용 화면으로 유지하되, 관리자 커스텀 믹싱 화면으로 운영 가능한 흐름을 제공해야 한다.
- **PRD-FR-060**: 관리자 전용 커스텀 믹싱은 서버에서 `ADMIN_EMAILS` 권한과 관리자 소유 `USER` 보컬 프로필을 검증하고, 업로드한 target audio를 요청 처리 중에만 Modal SoulX 믹싱 GPU 함수로 전달해야 한다. reference는 선택한 프로필의 저장된 reference asset을 사용하며, custom target 원본을 Leemage·PostgreSQL·프로젝트 파일에 영구 저장하거나 일반 사용자 믹싱 큐·티켓을 생성하지 않아야 한다. 관리자는 처리 상태와 결과 오디오를 확인할 수 있어야 한다.
- **PRD-FR-061**: 개발용 `/dev/svc`와 독립 목록 `/mixing-history`, `/vocal-profiles` 경로는 공개 제품 진입점에서 제거해야 한다. `/vocal-profiles/[id]` 상세는 기존 분석 결과·믹싱 연결을 위해 유지하고 목록 복귀는 `/library?tab=profiles`로 통합해야 한다.
- **PRD-FR-062**: 사용자-facing 제품 카피는 현재 구현과 실제 제공 기능을 사실대로 설명하고, 행동 결정에 필요하지 않은 반복·장문 설명이나 내부 구현 세부를 노출하지 않아야 한다. 문장형 카피는 기존 제품의 자연스러운 `~요` 존댓말 톤을 일관되게 사용하되 버튼·메뉴·탭·짧은 라벨은 기능에 맞는 간결한 명사형/행동형 표현을 유지한다. 동일 개념은 화면 전반에서 일관된 용어를 사용하고, 상태·오류·도움말은 사용자가 다음 행동을 판단하는 데 필요한 정보만 간결하게 제공해야 한다. 추상적인 홍보 문구, 근거 없는 과장, 상투적인 친절 표현, 불필요한 감탄·수식·반복처럼 AI가 생성한 듯한 범용 문장을 피하고 해당 화면의 실제 상태와 행동에 직접 연결되는 구체적인 표현을 우선해야 한다.
- **PRD-FR-063**: 보컬 분석 사용량은 종류 기반 티켓으로 관리한다. 기존 단일 티켓은 `VOCAL_ANALYSIS` 분석 티켓과 `AI_MIXING` 믹싱 티켓의 별도 지갑으로 일반화하고, 기존 `User.ticketBalance`와 기존 원장은 데이터 손실 없이 `AI_MIXING`으로 이전해야 한다. 가입 지급은 `SIGNUP_VOCAL_ANALYSIS_TICKET_GRANT`(기본 5)와 `SIGNUP_MIXING_TICKET_GRANT`(기본 1), 분석 비용은 `VOCAL_PROFILE_ANALYSIS_TICKET_COST`(기본 1), 믹싱 비용은 기존 `MIXING_TICKET_COST`를 서버 설정으로 관리한다. 새 보컬 분석은 분석 티켓을 서버에서 검증하고 정상 job 접수 시 분석 티켓을 한 번 차감하며 terminal failure에서 접수 당시 비용을 한 번 환불한다. 성공한 프로필을 삭제해도 분석 티켓은 복구하지 않는다. `USER` 보컬 프로필 자체에는 최대 보유 개수 제한을 두지 않으며 현재 보유 수 때문에 새 분석을 차단하거나 삭제를 요구하지 않는다. 분석 화면은 분석 티켓 잔액과 비용을 명확히 표시하고, 계정 메뉴·계정 내역·관리자 조정은 분석/믹싱 티켓 종류를 명시해야 한다. 분석 또는 AI 믹싱처럼 티켓을 실제 소모하는 사용자 액션은 비용이 0보다 클 때 티켓 종류와 수량을 보여주는 확인 모달에서 사용자가 명시적으로 승인한 뒤에만 mutation을 실행하며, AI 믹싱 재시도처럼 새 티켓 차감이 발생하는 경로도 동일하게 확인해야 한다. 클라이언트 확인은 보안 권한으로 신뢰하지 않고 기존 서버 잔액·idempotency·환불 검증을 유지한다. 클라이언트는 정책 환경변수를 직접 읽지 않고 서버 응답만 사용하며 기존 사용자당 동시 분석 1개 제한, 프로필 삭제·추천·믹싱 계약은 유지한다.
- **PRD-FR-064**: 공용 `VoiceOrb`의 내부 핑크·라벤더·보라 색 전환은 dominant RGB channel 전환이나 좁은 밝기/색 보간 때문에 얇은 선·띠처럼 읽히지 않도록 연속적으로 혼합해야 한다. live WebGL shader는 alpha/color normalization을 연속적인 계산으로 유지하되 기존 hard-max보다 전체 alpha를 체계적으로 높여 orb가 진하고 불투명해지지 않아야 하며, 저주파·저진폭의 기존 noise를 색 phase warp에만 사용해 중간색 영역을 넓힌다. 내부 경계 완화 후에도 F032 적용 전과 비슷한 가볍고 반투명한 밀도를 유지해야 한다. WebGL drawing buffer와 fragment output은 명시적으로 같은 alpha 표현 계약을 사용하고 GLSL 사양에서 정의된 falloff 계산만 사용해, iPhone Safari를 포함한 지원 브라우저의 실시간 합성에서 투명 canvas 직사각형이 배경과 다른 흰색으로 드러나거나 브라우저별로 orb 형태가 달라지지 않아야 한다. 이 개선을 위해 orb 외곽 `edgeMask`, silhouette, 크기, `ORB_MOTION_SPEED_SCALE`, 기존 public props를 변경하지 않으며, WebGL 실패 또는 reduced-motion fallback도 부드러운 내부 색 전환과 유사한 반투명 밀도를 제공해야 한다. 새 texture·render pass·dependency는 추가하지 않고 로그인·랜딩·voice-signal-core의 기존 레이아웃과 상태 동작을 유지한다.
- **PRD-FR-065**: 사용자-facing 분석과 추천 용어는 내부 계산 필드와 분리한다. `voiced ratio`는 `유효 음성 구간`, p10–p90 tessitura는 `주요 음역`, p50은 `중심 음`으로 표현하고, 음높이는 한국어 계이름과 국제 음이름을 함께 표시한다. 내부 MIDI·RMS·clipping·sample-rate·pitch-stability 값은 저장·검증·운영에 계속 사용할 수 있으나 사용자 행동에 필요하지 않은 성공 화면과 프로필 목록에서는 숨긴다. 추천 scoring은 새 version으로 변경해 신뢰도 상수 가산을 제거하고, 사용자-facing 추천 점수·순위·기본 정렬을 하나의 결정적 ranking 기준으로 통일한다.
- **PRD-FR-066**: 목소리 입력은 자동 마이크 녹음의 내부 파일명을 사용자-facing 준비 화면에서 숨기되 사용자가 직접 선택한 업로드 파일명은 확인 정보로 유지하고, idle/error 상태의 `녹음 시작`·`마이크 다시 시도`와 `녹음 파일로 분석하기` action을 같은 폭으로 제공해야 한다. 추천 목록은 기존 click-to-load YouTube facade를 유지하면서 행의 비상호작용 영역을 클릭하거나 keyboard로 실행해 곡 선택과 영상 미리보기를 함께 toggle할 수 있어야 하며, Thumbnail·AI 믹싱 같은 독립 control은 중복 실행하지 않아야 한다. 완료된 AI 믹싱은 추천 화면에서 중복 인라인 player를 펼치지 않고 `믹싱 결과 보기`로 `/library/mixes/{jobId}` 정본 상세에 연결해야 한다. 헤더 Bell은 읽지 않은 최신 알림만 표시하고 읽음 처리된 항목을 즉시 제거하되 전체 알림 페이지는 읽은 항목을 포함한 이력을 유지해야 한다. 아이콘 색은 성공·주의·오류·알림 유형·오디오/데이터처럼 의미가 있는 위치에서만 semantic token으로 보조하고 navigation·일반 action icon은 control foreground를 상속해야 한다. 공용 오디오 waveform player는 음소거 왼쪽의 compact 속도·음량 icon trigger와 접근 가능한 Popover로 재생속도 preset과 연속적인 음량 조절을 제공하고, 속도 변경 시 보컬의 pitch를 보존하며 기존 재생·seek·mute·segment 동작을 유지해야 한다.
- **PRD-FR-044**: 새 AI 믹싱 성공 결과는 SoulX 자동 반주 믹싱에서 `vocal-balance-v2`(생성 보컬 -2.0 dB, 반주 0.0 dB, 기존 pitch shift 및 peak protection 유지)을 적용한 뒤, 사용자에게 저장·재생·다운로드되기 전에 고정된 `clarity-normal-v1` finalization을 거쳐야 한다. finalization은 저중역 정리, 보컬 presence/air 강조, 가벼운 stereo widening과 -14 LUFS / -1 dBTP loudness 정리를 포함하며 최종 44.1 kHz stereo AAC/M4A encode와 같은 FFmpeg 경계에서 처리해야 한다. finalization 실패 시 미보정 SoulX 결과를 성공 결과로 fallback하지 않고 기존 submitted job을 재사용하는 bounded retry를 적용해야 한다.

### 인증과 사용자 소유권

- **PRD-FR-023**: 웹 앱은 Better Auth의 Google OAuth 로그인만 제공하고 이메일/비밀번호 및 다른 소셜 로그인 공급자를 활성화하지 않아야 한다.
- **PRD-FR-024**: 보컬 프로필, 추천 실행, 믹싱 작업, 저장 파일과 티켓 원장은 인증된 사용자에게 귀속되어야 하며 일반 사용자는 다른 사용자의 리소스를 조회·수정할 수 없어야 한다.
- **PRD-FR-025**: 제품 프로필·추천·믹싱·히스토리 API와 화면은 인증 세션을 요구하고, 인증되지 않은 사용자는 로그인 흐름으로 안내해야 한다. 개발용 SVC Workbench는 명시적인 개발 환경 설정에서만 별도로 허용한다.
- **PRD-FR-026**: 관리자는 서버 전용 `ADMIN_EMAILS` allowlist에 포함된 Google 계정으로 판별하고, 일반 사용자에게 관리자 API와 화면을 노출하지 않아야 한다.
- **PRD-FR-067**: 신규 사용자가 Google 로그인을 마치고 처음으로 인증된 제품 화면에 진입하면, 웹 앱은 Copysinger의 보컬 분석→노래 추천→AI 믹싱 흐름과 분석 티켓·믹싱 티켓의 용도를 3단계의 가벼운 온보딩 모달로 안내해야 한다. 모달은 기존 Copysinger 브랜드 마크와 제품의 생성 퍼널 stepper UI를 재사용하고, 단계별 아이콘·색은 semantic token을 실제 오디오·데이터 의미와 진행 상태에 맞게 사용해야 한다. 티켓 수량은 클라이언트에 하드코딩하지 않고 해당 단계에서 서버가 지급한 현재 잔액을 표시하며, 사용자가 마지막 단계의 명시적인 완료 action을 선택한 경우에만 사용자별 완료 시각을 서버에 멱등적으로 저장한다. 완료된 사용자는 재로그인·다른 기기·다른 제품 경로에서도 다시 안내하지 않고, 기존 가입자는 배포 시 완료 상태로 이관해 새 온보딩을 소급 노출하지 않는다. 단순 조회·렌더링·단계 이동은 완료로 기록하지 않으며, 인증된 사용자는 자신의 상태만 조회·완료할 수 있어야 한다.

### 오디오 영구 저장

- **PRD-FR-027**: 분석에 성공한 사용자 레퍼런스 오디오는 Leemage의 서버 전용 API Key를 사용해 업로드하고, PostgreSQL에는 Leemage project/file ID, URL, MIME, 크기와 생명주기 상태만 저장해야 한다.
- **PRD-FR-028**: 합성에 성공한 결과 오디오는 Modal에서 Leemage로 복사한 뒤에만 작업을 최종 성공 처리하고, 이후 재생·다운로드는 사용자 소유권을 검증하는 웹 API를 통해 제공해야 한다.
- **PRD-FR-029**: 보컬 프로필이나 믹싱 이력 삭제 시 연결된 Leemage 파일도 삭제해야 하며, 외부 삭제 실패는 재시도 가능한 정리 상태로 기록해야 한다.

### 티켓과 믹싱 큐

- **PRD-FR-030**: 신규 사용자에게 `SIGNUP_TICKET_GRANT`만큼 티켓을 정확히 한 번 지급하고, 믹싱 비용은 `MIXING_TICKET_COST`로 설정해야 한다.
- **PRD-FR-031**: 믹싱 큐 등록과 티켓 차감은 하나의 DB 트랜잭션으로 처리하며 잔액 부족, 중복 요청 또는 동일 idempotency key 재시도에서 추가 차감하거나 작업을 중복 생성하지 않아야 한다.
- **PRD-FR-032**: Modal 작업 접수 전에 입력 준비나 시스템 오류로 실패하면 티켓을 자동 환불하고, Modal 작업이 접수된 뒤 발생한 실패에는 티켓을 환불하지 않아야 한다.
- **PRD-FR-033**: 티켓의 지급·사용·환불·관리자 조정은 불변 원장으로 저장하고 각 항목은 잔액 변화량, 유형, 관련 믹싱 작업, 설명과 발생 시각을 포함해야 한다.
- **PRD-FR-034**: 믹싱은 PostgreSQL 영속 큐와 별도 worker가 처리하고 `pending → preparing → submitted → processing → succeeded | failed | canceled` 상태, 시도 횟수와 오류를 저장해야 한다.
- **PRD-FR-035**: worker는 경쟁 실행과 서버 재시작에서도 하나의 작업을 한 번만 점유하고, 중단된 작업을 재개하거나 안전하게 재시도해야 하며 설정된 동시성 한도를 준수해야 한다.
- **PRD-FR-036**: 믹싱 히스토리는 현재 선택된 보컬 프로필이나 추천 실행과 독립된 사용자 소유 목록으로 제공하고 곡, 사용 프로필, 상태, 티켓, 생성·완료 시각과 결과를 표시해야 한다.
- **PRD-FR-037**: 마이 페이지는 사용자 기본 정보, 현재 티켓 잔액과 페이지네이션된 티켓 원장을 제공해야 한다.
- **PRD-FR-038**: 관리자 페이지는 사용자 수·작업 상태 집계, 사용자 및 믹싱 작업 검색·필터, 티켓 원장 조회와 사유가 필수인 티켓 증감 기능을 제공해야 한다.

### 제품 UI와 탐색

- **PRD-FR-045**: 웹 앱은 white·neutral gray·black 중심의 공통 semantic token, 절제된 radius·border·shadow, 명확한 typography와 spacing 위계를 사용해야 하며 waveform, 분석 결과와 상태처럼 의미 있는 콘텐츠에만 제한적으로 accent color를 사용해야 한다. 넓은 canvas에 beige·cream·yellow chroma를 사용하지 않아야 한다. 랜딩과 분석 진행의 중앙 visual에는 React Bits Orb를 Copysinger accent로 조정해 사용할 수 있으며, reduced-motion·WebGL 미지원 환경에서 의미와 action이 유지되는 정적 fallback을 제공해야 한다.
- **PRD-FR-046**: 루트 진입 화면은 인증 없이 제품 가치와 핵심 흐름을 설명하고 Google 로그인 또는 인증된 음성 스캔으로 연결해야 한다. x.ai의 작은 announcement, 절제된 중앙형 hero, 넓은 여백, 비대칭 product bento, editorial product demo, hairline metric band와 2-up CTA 구조를 Copysinger의 분석·추천·믹싱 내용으로 재해석한다. Aceternity UI와 React Bits의 실제 source pattern을 활용하되 기존 랜딩의 장식 waveform, dotted motion, ripple과 긴 반복 sticky card는 사용하지 않는다. 마지막 CTA 아래에는 실제 site footer를 제공하며 crystal/prism 이미지는 사용하지 않는다. 로그인 화면은 제품 로고, `Copysinger` 이름, muted `계속하려면 로그인하세요.` 안내와 Google icon을 포함한 `구글로 시작하기` action을 중심 콘텐츠로 제공하고, action 아래에는 Google 로그인 시 Copysinger의 이용 약관 및 개인정보 처리방침에 동의한다는 안내를 표시해야 한다. 다른 공급자나 이메일 가입이 가능한 것처럼 표시하지 않으며 OAuth 진행·설정 누락·실패 상태는 조건부로 안내한다.
- **PRD-FR-047**: 음성 스캔은 기존 녹음·업로드·검증·durable analysis job 계약을 유지하면서 마이크 권한, live waveform, 경과 시간, 서버 최소 유효 길이 5초, 약 10초의 권장 녹음과 최대 60초, 중지·재시도·오류 상태를 명확히 표시해야 한다. 분석 진행률과 단계는 서버에서 확인할 수 있는 상태보다 더 정밀한 진행을 가장하지 않아야 한다.
- **PRD-FR-048**: 보컬 프로필 화면은 관측 음역, 주요 음역, 중심 음, 유효 음성 구간과 핵심 특성을 우선 요약하고 histogram, pitch trace와 reference band 오디오를 세부 근거로 보존해야 한다. B3·D4 같은 서양 음이름은 `시3(B3)`, `레4(D4)`처럼 한국어 계이름과 함께 표시하고, raw MIDI 숫자와 MIDI 자체에 대한 사용자-facing 설명은 숨긴다. 피치 안정도·클리핑·RMS·샘플레이트는 내부 분석/품질 계약에 남길 수 있으나 성공한 프로필의 핵심 정보나 보컬 프로필 목록 컬럼으로 노출하지 않는다. `주요 음역 폭은 약 N반음/옥타브` 같은 별도 폭 문장은 표시하지 않고, 중심 음을 포함한 관찰 결과에서 성별·성종·장르 적합도 같은 검증되지 않은 속성을 추정하지 않아야 한다.
- **PRD-FR-049**: 추천 목록은 현재 API가 제공하는 곡·아티스트·단일 추천 점수·추천 키·이유·믹싱 가능 여부를 기준으로 검색·정렬·필터링할 수 있어야 한다. `추천 적합도`와 `종합 추천 순위`처럼 서로 다른 기준을 동시에 기본 정렬 옵션으로 제공하지 않으며, 기본 표시 순위와 기본 정렬은 단일 추천 점수와 일치해야 한다. 곡 상세는 동일한 보컬 프로필·카탈로그·scoring revision 조합에서 원키 적합도, 추천 키 적합도, 추천 점수와 실제 음역 근거를 구분해 보여주고, 사용자와 곡 모두의 중심 음을 같은 기준으로 비교할 수 있어야 한다. 별도 `키 조정 변화` 점수는 표시하지 않으며, 앨범 이미지·장르·난이도·가사·인앱 미리듣기처럼 현재 계약에 없는 값을 생성하거나 암시하지 않아야 한다.
- **PRD-FR-050**: AI 믹싱 UI는 영속 작업의 실제 상태를 이해하기 쉬운 단계로 매핑하고 대기·재시도·실패·성공을 구분해야 한다. 라이브러리는 기존 사용자 소유 보컬 프로필과 믹싱 이력을 통합 탐색할 수 있게 하며, 결과 상세에서 저장된 오디오 재생·다운로드와 기존 삭제 동작을 제공해야 한다. 사용자가 노래를 직접 부른 원본과 AI 결과의 Before/After 비교는 해당 녹음 도메인이 구현되기 전까지 표시하지 않아야 한다.
- **PRD-FR-051**: 인증 제품 화면은 데스크톱에서 persistent sidebar 없이 브랜드·중앙 제품 navigation·우측 계정 메뉴를 담은 공통 top header를 사용하고, 모바일에서는 접근 가능한 compact navigation을 제공해야 한다. 계정 메뉴 최상단에는 현재 사용 가능한 티켓 수를 표시하고 메뉴를 다시 열 때 최신 잔액을 조회해야 한다. 비로그인 header는 중복 가입 CTA 없이 primary `로그인` action 하나만 제공한다. 제품 화면은 focus-visible, 명시적인 button label, 키보드 조작, reduced-motion 배려와 loading·empty·error·disabled 상태를 제공해야 하며 공통 상태와 핵심 오디오 상호작용은 Storybook에서 독립적으로 검증할 수 있어야 한다.
- **PRD-FR-052**: 사용자가 제공한 32×32 SVG의 일곱 막대 파형 silhouette을 Copysinger의 공통 app mark로 사용하고 기존 AI 생성 헤드폰 bitmap을 대체해야 한다. mark에는 기존 brand token과 대응하는 violet–blue–pink 연속 gradient를 적용하며, header/footer/login의 로고와 favicon은 같은 벡터 master 자산에서 파생하고 16px부터 식별 가능한 geometry, 투명 배경, 접근 가능한 제품명을 유지해야 한다. 서비스명은 공백 없는 `Copysinger`로 표기하고 공통 wordmark에는 제공된 Paperlogy 7Bold를 self-host해 사용해야 한다. 검색·공유 표면은 흰 배경 중앙에 작은 mark, Paperlogy `Copysinger`, `Find your voice. Sing your Match`를 배치한 1200×630 Open Graph image, canonical home URL, public sitemap·robots를 제공하며 인증 제품·관리자·개발 화면은 index 대상에서 제외해야 한다.
- **PRD-FR-053**: 로그인 화면과 제품 footer의 `이용 약관` 및 `개인정보 처리방침`은 각각 공개 route로 연결되어야 한다. 문서는 현재 구현의 Google 인증, 음성 녹음·분석, 추천, 티켓 기반 AI 믹싱, 외부 저장·처리와 삭제 계약을 사실대로 설명하고, 확인되지 않은 운영자 연락처·국외 처리 지역은 임의로 생성하지 않아야 한다.
- **PRD-FR-054**: 성공적으로 생성된 사용자 보컬 프로필은 사용자별 단조 증가 번호를 사용한 `보컬 프로필 N` 기본 이름을 영속 저장해야 한다. 삭제된 번호를 재사용하거나 기존 프로필을 재번호화하지 않아야 하며, 사용자는 본인 프로필의 이름을 공백 제거 후 1~40자로 변경할 수 있어야 한다.
- **PRD-FR-055**: 보컬 프로필 목록은 기존 파형 glyph 대신 프로필 ID에서 결정적으로 생성한 square grainy gradient 커버를 표시해야 한다. 같은 프로필은 이름 변경과 재접속 후에도 같은 커버를 유지하고, 서로 다른 프로필은 구분 가능한 색 조합을 가져야 한다.
- **PRD-FR-056**: 추천 목록과 곡 상세는 저장된 카탈로그 `sourceVideoId`가 유효한 곡에 한해 원본 YouTube 영상을 16:9 player로 제공해야 한다. 목록은 사용자가 재생을 선택하기 전 실제 iframe을 만들지 않는 click-to-load facade를 사용하고, 상세는 제목 위에 privacy-enhanced embed를 표시하며 별도 `외부 출처 열기` action은 제거해야 한다.
- **PRD-FR-057**: 추천 결과는 `RecommendationRun`·`RecommendationItem` 스냅샷으로 영속하지 않고 현재 보컬 프로필, 공개 카탈로그 revision과 scoring version으로 요청 시 계산해야 한다. 프로필 상세는 `추천 결과 보기` action으로 현재 결과에 접근하며, TanStack Query 캐시는 동일 revision 조합에서만 재사용해야 한다. 분석에서 믹싱용 중앙 대표 구간을 확보하지 못한 경우 결과 화면에 누락 상태를 명시하고, 추천 목록·곡 상세는 AI 믹싱 action을 실행 전에 비활성화하며 새 보컬 분석 경로를 안내해야 한다. 믹싱 작업은 검증된 보컬 프로필·곡 분석·target asset·추천 키·scoring revision 입력을 영속해 카탈로그 변경 후에도 작업 근거를 유지해야 한다.
- **PRD-FR-058**: 인증 제품 header는 계정 메뉴 왼쪽(모바일에서는 제품 메뉴 왼쪽)에 접근 가능한 알림 Bell과 읽지 않은 수 badge를 표시해야 한다. 인앱 알림은 관리자에 의한 양수 티켓 조정, 보컬 프로필 분석 성공·최종 실패, AI 믹싱 성공·최종 실패에 대해 terminal 상태당 한 번만 생성하고 관련 계정·프로필·라이브러리 상세로 이동해야 한다. 가입 지급과 믹싱 환불은 별도 티켓 알림으로 중복 생성하지 않으며, retry 중간 상태·내부 오류 상세를 사용자에게 노출하지 않아야 한다. 사용자는 최신 알림, 전체 알림 이력, 개별 읽음과 모두 읽음을 사용할 수 있어야 한다.

## 데이터 요구사항

- **PRD-DATA-001**: PostgreSQL을 단일 영속 데이터베이스로 사용한다.
- **PRD-DATA-002**: Prisma schema와 migration을 데이터 모델의 SSOT로 사용한다.
- **PRD-DATA-003**: 로컬 개발용 PostgreSQL은 사용자가 실행하는 `docker compose up`으로 시작할 수 있어야 한다.
- **PRD-DATA-004**: 오디오 바이너리는 PostgreSQL에 직접 넣지 않고 파일 참조와 메타데이터만 저장한다.
- **PRD-DATA-005**: 분석 결과의 전체 원시 frame 배열은 저장하지 않는다. UI 시각화에 필요한 음정 histogram과 크기가 제한된 다운샘플 피치 series만 집계 descriptor로 저장할 수 있다.
- **PRD-DATA-006**: 카탈로그 분석용 임시 다운로드와 분리 stem은 프로젝트 저장소나 영구 볼륨에 보관하지 않고 작업별 OS 임시 디렉터리에서 처리한다. 별도로 사용 권한을 확보한 AI 믹싱 target만 관리자 업로드를 거쳐 외부 저장소에 장기 저장할 수 있으며, PostgreSQL에는 target asset 참조·SHA-256·source revision 연결과 집계 분석값·도구 버전을 저장한다. 관리자 snapshot에는 이 metadata만 포함하고 원본 bytes는 포함하지 않는다.
- **PRD-DATA-007**: PostgreSQL에는 믹싱 작업의 외부 job ID·상태·오류와 Leemage 파일 참조만 저장하고 원곡·reference·결과 오디오 바이너리는 저장하지 않는다.
- **PRD-DATA-008**: Better Auth 사용자·세션·계정·검증 스키마와 제품 사용자 소유 관계는 Prisma schema와 migration으로 관리한다.
- **PRD-DATA-009**: 티켓 원장은 append-only로 유지하고 현재 잔액은 원장과 일치하도록 DB 제약 및 트랜잭션으로 보호한다.
- **PRD-DATA-010**: 사용자 레퍼런스, 믹싱 결과와 사용 권한이 확인된 카탈로그 mixing target은 Leemage에 저장한다. 그 외 분석용 다운로드·분리 stem·작업 중간 파일은 영구 저장하지 않으며, 카탈로그 이동은 관리자 snapshot import/export로 수행한다.
- **PRD-DATA-011**: 사용자 보컬 프로필의 표시 이름과 사용자별 기본 이름 순번은 Prisma schema와 migration으로 관리해야 한다. 기존 사용자 프로필은 사용자별 생성 시각과 ID의 결정적 순서로 backfill하고 곡 분석용 프로필에는 사용자 표시 이름을 적용하지 않아야 한다.
- **PRD-DATA-012**: 인앱 알림은 사용자 소유 PostgreSQL row로 영속 저장하고 type, 사용자용 제목·메시지, 내부 경로, source identity, dedupe key, 읽은 시각과 생성 시각을 포함해야 한다. 같은 terminal event의 worker 재실행과 ticket idempotency 재시도는 중복 알림을 만들지 않아야 하며 다른 사용자의 알림을 조회·수정할 수 없어야 한다.
- **PRD-DATA-013**: 곡 identity와 카탈로그 순위는 분리하고, 영상 출처와 곡 분석 결과는 교체 시 덮어쓰지 않는 revision으로 저장해야 한다. 추천 실행은 사용한 곡 분석 revision을 참조해 이후 관리자 변경과 무관하게 당시 결과를 추적할 수 있어야 한다.
- **PRD-DATA-014**: 관리자 커스텀 믹싱 target은 요청 처리 중 메모리 또는 OS 임시 영역에서만 사용하고 영구 저장하지 않는다. Modal 결과도 작업 TTL과 삭제 계약을 따르며, custom target을 영속 asset row나 카탈로그 target으로 승격하지 않는다.

## 비기능 요구사항

- **PRD-NFR-001 보안**: DB 비밀번호, Better Auth secret, Google OAuth secret, `MODAL_API_KEY`와 Leemage API Key는 `.env.local` 또는 Secret에만 두고 Git과 클라이언트 번들에 포함하지 않는다.
- **PRD-NFR-002 개인정보**: 녹음과 합성 결과는 삭제 가능해야 하며 보관 기간을 명시한다.
- **PRD-NFR-003 비용**: 프로필·곡 분석은 Modal CPU에서 수행하고 합성 데모만 Modal GPU를 사용한다.
- **PRD-NFR-004 재현성**: 보컬 프로필·카탈로그·곡 분석 revision과 scoring version으로 추천 결과를 재계산할 수 있어야 하며, 영속 믹싱 작업은 접수 시 검증한 revision 입력을 보존해야 한다.
- **PRD-NFR-005 품질**: 변경 시 TypeScript 검사, ESLint, 프로덕션 빌드, Prisma validation과 관련 테스트를 통과해야 한다.
- **PRD-NFR-006 책임 있는 사용**: 사용 권한이 있는 음성과 음악만 처리하도록 고지하고, 결과를 의료적 평가로 표현하지 않는다.
- **PRD-NFR-007 설명 가능성**: 추천 이유는 음역 겹침, 고음/저음 부담, 키 이동 효과처럼 검증 가능한 항목에서 생성한다.
- **PRD-NFR-008 비용·동시성**: 추천 조회만으로 Modal 합성 비용이 발생하지 않아야 하며, 사용자가 명시적으로 요청한 곡만 합성하고 동일 항목의 중복 시작을 idempotent하게 차단하며 Modal 동시성 정책에 따른 대기 상태를 사용자에게 숨기지 않는다.
- **PRD-NFR-009 인증·권한**: 모든 사용자 및 관리자 API는 서버에서 세션과 리소스 소유권 또는 관리자 권한을 검증해야 하며 UI 숨김만을 접근 통제로 사용하지 않는다.
- **PRD-NFR-010 작업 내구성**: 브라우저 종료나 웹 서버·worker 재시작 후에도 접수된 믹싱 작업, 티켓 결제 결과와 사용자 조회 상태가 소실되지 않아야 한다. 단일 인스턴스의 기본 `dev`·`start` 명령은 웹과 worker를 함께 시작해 접수된 작업이 별도 수동 실행 없이 처리되어야 한다.
- **PRD-NFR-011 외부 저장소**: Leemage 429 응답의 `Retry-After`를 준수하고 재시도 가능한 오류에는 제한된 지수 백오프를 적용하며, 업로드 confirm과 DB 기록 간 부분 실패를 정리할 수 있어야 한다.
- **PRD-NFR-012 분석 배포 단일화**: 사용자 보컬 프로필과 곡 카탈로그 분석은 인증된 Modal CPU 서비스만 사용해야 한다. 웹 런타임의 local/Modal 선택기, 로컬 FastAPI 분석 서비스와 Docker Compose 분석 컨테이너를 제공하지 않으며, 공유 Python 분석 코어는 Modal 서비스 패키징과 회귀 테스트를 위한 runtime-neutral 모듈로 유지해야 한다.

## 보컬 프로필 MVP 정의

초기 추천에는 음색 유사도보다 음역 적합성이 중요하므로 아래 통계부터 사용한다.

- pitch: `min`, `max`, `p10`, `p50`, `p90` MIDI
- tessitura: voiced pitch의 중앙 80% 구간
- stability: cents deviation 기반 변동성
- quality: duration, voiced ratio, clipping ratio, RMS
- optional descriptors: MFCC mean/std, spectral centroid
- metadata: analyzer name/version, sample rate, created time

음색 embedding은 추천 품질 개선 가설이 검증될 때 별도 feature로 추가한다.
