# Feature Spec: production-readiness-core

## 개요

- **기능 ID**: JCXFBTGYM8R3
- **기능명**: 백엔드 운영 안정성 핵심 5개 개선
- **대상 레포**: copy-singer-web
- **작성일**: 2026-09-13
- **상태**: Approved
- **주 컴포넌트**: web
- **교차 컴포넌트**: data, modal-api

## 목적

Production Readiness Audit에서 선정한 5개 개선을 하나의 Feature로 구현한다. 작은 단일 웹 인스턴스와 PostgreSQL, 별도 worker 및 Modal이라는 현재 구조에서 요청 폭주와 부분 장애가 중복 비용, 무기한 작업, 파일 유실, 기존 사용자 인증 실패로 이어지는 경로를 닫는다.

## 사용자 스토리

### US-1: 재시작에도 작업과 티켓 상태를 신뢰한다

사용자는 worker 재시작·외부 응답 유실 후에도 작업이 복구되거나 명확한 최종 상태로 끝나고, 중복 티켓 차감과 잘못된 환불이 발생하지 않기를 원한다.

**Acceptance Criteria:**
- [x] AC-01: 세 worker의 오래된 lease 소유자는 성공·실패·환불 등 영속 상태를 변경할 수 없다.
- [x] AC-02: 마지막 허용 시도 중 강제 종료한 작업이 lease 만료 후 영구 활성 상태로 남지 않고 복구 또는 최종 실패로 수렴한다. 보컬 분석의 다음 요청도 가능해진다.
- [x] AC-03: 같은 외부 제출의 동시 요청·응답 유실·재시도는 같은 제출 식별자로 처리하고 중복 실행을 방어한다. 접수 여부 불명 상태는 제한된 복구 후 FR-1의 종료·환불 표에 따라 처리하며, 믹싱의 불명 접수를 미접수 환불로 오인하지 않는다.

### US-2: 느린 의존성과 요청 폭주에도 예측 가능한 응답을 받는다

사용자는 제한된 처리량을 초과했을 때 빠르고 명확한 안내를 받고 정상 polling과 오디오 탐색을 계속 사용할 수 있기를 원한다.

**Acceptance Criteria:**
- [x] AC-04: Leemage presign/PUT/confirm/delete, Modal 호출과 polling, DB 연결/쿼리, FFmpeg는 명시적 시간 예산을 가진다. 시간 초과 시 자원과 점유권을 안전하게 정리한다.
- [x] AC-05: 일시적인 DB·외부 서비스 오류는 제한된 backoff로 처리하고 원인이 기록된다. 무기한 루프·미종료 subprocess가 남지 않는다.
- [x] AC-06: 요청 제한 및 upload slot 확보는 대용량 body 읽기 전에 수행한다. 읽기 실패·취소·제한 초과 후 slot이 반환된다.
- [x] AC-07: 사용자별·전역 큐 수용량을 초과한 동시 접수는 DB 수준에서 제한하며 거절된 요청은 티켓을 차감하거나 외부 AI를 제출하지 않는다. 동일 요청 재전송은 기존 job을 반환한다.
- [x] AC-08: 정상 분석 polling(1.5~3초), 믹싱 polling(5초), 알림 polling(30초) 및 Range 재생을 제한 정책이 수용한다. 429는 Retry-After를 제공하고 전역 수용 불가는 일관된 503/재시도 안내를 제공한다.
- [x] AC-09: 임의 X-Forwarded-For로 사용자 제한을 우회할 수 없다. IP 보조 제한의 신뢰 프록시 설정과 단일 프로세스 제한의 다중 인스턴스 한계를 명시한다.

### US-3: 삭제한 파일과 사용하는 파일의 상태가 일치한다

사용자는 삭제 접수 뒤 재시작되어도 파일 정리가 이어지고 삭제와 믹싱 생성의 경쟁으로 사용할 파일이 사라지지 않기를 원한다.

**Acceptance Criteria:**
- [x] AC-10: 프로필 삭제와 믹싱 생성의 경쟁에서는 둘 중 하나의 유효한 상태가 확정되며 접수된 작업이 사용하는 외부 파일을 선행 삭제하지 않는다.
- [x] AC-11: DB 삭제 확정 직후 종료되어도 cleanup 의도가 남는다. 사용자 음성·결과와 catalog target 삭제 재시도는 모두 추적 가능하고 404도 멱등적 성공으로 처리한다.
- [x] AC-12: 외부 업로드 후 DB 기록 실패, confirm 응답 유실, 결과 저장 중 lease 유실은 로컬 intent와 확보한 외부 identity로 추적한다. 자동 정리 보장은 FR-4의 검증된 provider 계약 범위로 한정하며, presign 응답 유실로 identity를 얻지 못한 경우도 운영자 확인 대상으로 남긴다.

### US-4: 신규 가입 정책 변경 후에도 기존 계정을 사용할 수 있다

**Acceptance Criteria:**
- [x] AC-13: 기존 사용자에게 5장을 지급한 뒤 신규 지급량을 3장으로 바꿔도 해당 사용자의 세션과 API가 정상 동작하고 기존 잔액·원장은 바뀌지 않는다.
- [x] AC-14: 가입 hook 또는 복구의 중복·동시 실행은 종류별 가입 원장을 한 번만 만든다. 부분 가입 지급 실패는 FR-5의 운영자 전용 CLI로 보완한다. 과거 가입자의 미지급 종류는 운영자 지정 금액, 이후 신규 가입은 영속 지급 의도에 기록한 당시 금액을 사용한다.
- [x] AC-15: 일반 세션 조회는 가입 지급 transaction을 호출하지 않는다. 티켓이 필요한 접수 경로의 잔액 검증·차감 원자성은 유지한다.

### 추가 실패 시나리오 인수 조건

- [x] AC-16: 외부 조회 영구 실패·복구 예산 소진 시 사용자 작업을 FAILED로 종료하고 활성 슬롯을 반환한다. 자동 재제출은 중단하며 뒤늦은 성공은 작업을 되살리지 않는다. 티켓은 FR-1 표대로 처리한다.
- [x] AC-17: presign 성공 후 응답 유실 검증은 실제 provider가 제공하는 조회·멱등성·TTL만 모사한다. 자동 식별 불가 구간은 unresolved intent로 남고 삭제 완료로 표시되지 않는다.
- [x] AC-18: 한 종류만 지급된 과거 계정을 정책 변경 후 운영자 지정 금액으로 복구해도 기존 원장은 불변이며, 중복·동시 복구는 한 번만 지급한다. 다른 금액으로 재실행하면 충돌로 거부한다.

## 기능 요구사항

### FR-1: 큐 복구와 외부 제출 식별자

세 worker의 lease 갱신, 조건부 상태 전이, 소진된 시도 복구를 맞춘다. 외부 제출 식별자와 요청 입력 충돌을 검증한다. 전송 재시도와 확정된 terminal failure 이후 새 연산은 구분한다. 성공 결과 확정 전 소유권 재검증과 미참조 결과 정리를 포함한다. 기존 알림 dedupe와 환불 정책을 유지한다.

#### 접수 상태별 종료·환불 정책

| 작업 / 확정된 상황 | 복구 예산 소진 후 사용자 상태 | 티켓 처리 | 후속 처리 |
| --- | --- | --- | --- |
| 보컬 분석 terminal failure (접수 여부 포함) | FAILED, 활성 슬롯 반환 | 접수 당시 분석 비용을 한 번 환불 | PRD-FR-063 유지. 소스·늦은 결과 정리 |
| 믹싱 미접수 확정 후 실패 | FAILED, 활성 슬롯 반환 | 접수 당시 믹싱 비용을 한 번 환불 | PRD-FR-032 유지 |
| 믹싱 접수 확정 후 실패 또는 완료 확인 deadline 초과 | FAILED, 활성 슬롯 반환 | 자동 환불 없음 | 확인 가능한 외부 작업 취소·정리 추적 |
| 믹싱 접수 여부가 끝내 불명 | FAILED, 활성 슬롯 반환, 사용자에게 확인 필요 안내 | 자동 환불 보류 | 별도 운영자 확인 기록 유지. 미접수 확인 시 원래 job의 환불 키로 한 번 환불, 접수 확인 시 무환불 |
| 곡 분석 실패·접수 불명 지속 | FAILED, 활성 슬롯 반환 | 사용자 티켓 없음 | 운영자 확인 대상으로 기록 |

- 불명 상태의 자동 복구 횟수와 시간은 plan에서 정하며, 사용자 활성 작업과 별도의 운영자 확인 기록으로 남긴다. 수동 확인 지연이 사용자의 다음 요청을 영구 차단하지 않는다.
- terminal 이후 뒤늦은 성공은 사용자 결과·성공 알림으로 다시 공개하거나 환불을 취소하지 않는다. 확보한 외부 identity로 취소/파일 정리를 예약하고, 자동 정리 불가 시 운영자 확인 기록을 유지한다.
- 같은 idempotency key는 terminal 이후에도 기존 job을 반환한다. 새로운 사용자 요청은 새 key와 통상 티켓 정책을 따른다. 불명 작업의 해제는 무한 무료 재실행을 뜻하지 않으며 요청 제한과 수용량 제한을 계속 적용한다.
- worker lease 보유자만 자동 작업 상태를 확정한다. terminal 이후 운영자 reconciliation은 별도 권한과 조건부 전이·불변 원장을 사용하고 원래 작업을 재활성화하지 않는다.

### FR-2: timeout과 deadline

일반 API, 큰 파일, subprocess, 장기 AI 작업의 시간 예산을 구분한다. 재시도는 전체 시간 예산을 소비하고 종료 시 AbortSignal·stream·subprocess·DB 자원 정리를 검증한다. queue runner는 복구 가능한 실패를 backoff하고 종료 신호 후 신규 claim을 멈춘다. 구체 기본값은 승인 후 plan에서 보수적으로 정의한다.

### FR-3: 요청·업로드·큐 수용량 보호

사용자 API(분석 접수 두 경로, 믹싱 접수, 추천, 상태 polling, 목록·티켓·알림, 오디오) 및 관리자 고비용 업로드/import/custom mixing에 비용에 맞는 제한을 적용한다. 사용자 제한을 기본으로 하고 인증 전 요청·IP 제한은 신뢰 프록시 경계와 함께 설계한다. body 읽기 전 가능한 인증·요청 키·잔액·활성 작업 사전 검사를 수행하되 최종 원자적 DB 검사를 대체하지 않는다. 전역 큐 수용량과 worker lane 수를 구분한다.

### FR-4: 파일 생성·삭제의 복구 가능성

삭제 의도와 cleanup 예약을 DB에서 먼저 확정하고 worker가 외부 파일을 정리한다. 파일 예약·업로드·confirm·DB 연결 단계 사이의 실패는 로컬 intent와 확보 가능한 외부 identity로 추적한다. 사용자/작업 소유권과 참조 무결성을 유지하며 catalog target도 정리 범위에 포함한다. 기존 진행 중 작업과 asset을 migration으로 유실하지 않는다.

#### Provider 계약 확인과 자동 복구의 한계

- plan 확정 전에 Leemage의 client identity/idempotency 지원, identity로 예약·파일을 조회하는 방법, 미확정 예약/object TTL, confirm 반복·응답 유실 처리, 삭제 404 의미를 문서 또는 접근 가능한 소스로 확인하고 근거를 plan/decisions에 기록한다. 확인 불가는 명시한다.
- 외부 요청 전에 로컬 intent를 기록한다. 반환받은 fileId/objectName은 후속 PUT 전에 영속하고, confirm·DB 연결 실패는 해당 identity로 재조회하거나 정리한다.
- presign 예약 성공 후 응답 유실 등 외부 identity를 확보하지 못한 구간은, 검증된 client identity 조회가 있을 때 자동 복구한다. 검증된 미확정 object TTL만 있다면 provider 만료 정책에 의존함을 명시하며 확인 전에는 로컬 삭제 완료로 처리하지 않는다.
- 조회와 TTL 모두 미지원 또는 확인 불가이면 intent를 운영자 reconciliation 대상으로 유지하고 자동 식별·삭제 보장에서 제외한다. provider에 없는 기능을 fake에 추가해 검증을 통과시키지 않는다.
- Feature 완료 조건은 식별 가능한 파일의 자동 정리, 식별 불가 intent의 영속 기록·운영자 조회/해결 절차, 한계의 운영 문서 공개다. 식별 불가 외부 파일이 실제로 제거됐다고 주장하지 않는다. Leemage 서비스 변경이 필요하면 별도 범위 승인 대상으로 남기며 이 Feature에서 임의 변경하지 않는다.

### FR-5: 세션과 가입 지급 분리

인증은 세션 조회를 담당하고 가입 지급은 가입 시점과 명시적 복구 경로가 담당한다. 기존 원장을 현재 환경변수 amount와 비교해 인증을 실패시키지 않는다. 지급량 변경은 변경 후 신규 가입의 지급 의도에만 적용한다. 신규 가입은 종류별 금액을 영속 지급 의도로 기록한 뒤 지급하고, 미완료 복구는 해당 금액을 사용한다. 일반 세션 조회는 지급 의도 생성·지급·복구를 수행하지 않는다.

- 과거 사용자 중 지급 의도가 없고 당시 지급량을 확인할 수 없는 누락분은 운영자가 금액을 명시한다. 현재 환경변수나 기존 다른 종류의 지급량으로 과거 정책을 추정하지 않는다.
- 복구는 서버 DB 접근 권한을 가진 운영자 전용 CLI로 제공한다. 사용자 웹 API나 자동 로그인 요청에 노출하지 않는다. 사용자·종류·금액·사유·운영자 식별 정보를 필수로 받고, dry-run 결과를 검토한 뒤 명시적 apply 옵션으로 실행한다.
- 신규 지급 의도가 이미 있으면 CLI도 그 금액을 따르며 다른 금액은 거부한다. 기존 가입 원장이 있으면 일치하는 재실행은 no-op, 다른 금액은 충돌로 거부하고 원장을 변경하지 않는다. 기존 누락 보너스가 아닌 추가 보상은 기존 관리자 조정 기능을 사용한다.
- 종류별 가입 identity를 공유하여 가입 hook과 복구 CLI의 동시 실행도 한 번만 지급한다. 복구 CLI의 정책은 사용자 동작이 아닌 운영 절차이며 이번 Feature 검증에서는 테스트 계정만 사용한다.

## 범위와 제외

- 포함: Next.js 서버, 세 durable worker, Prisma schema/migration, 필요한 Modal 제출 계약, 위 계약을 검증하는 테스트와 운영 문서.
- 제외: 추천 캐시·검색 성능 개선, 개인정보 문서 전면 개정, OAuth 암호화, 관리자 SSRF 개선, 전면 API 오류 재설계, 백업 시스템 구축. 이들은 감사 후속 범위이며 이번 Feature가 전체 production readiness를 보장하지 않는다.
- 새 Redis/Kafka/Kubernetes, 마이크로서비스 분리, 별도 전용 queue 제품은 도입하지 않는다.
- Next.js 공개 배포·실사용 부하 발생·실제 사용자 데이터 삭제를 수행하지 않는다. 검증은 격리 DB와 fake dependency를 우선한다.
- Modal 소스 변경과 로컬 계약 검증은 포함한다. 실제 원격 배포는 구현 결과·검증·호환 순서를 준비한 뒤 해당 시점에 명시한다. 배포 미실행을 운영 반영 완료로 기록하지 않는다.

## 비기능 요구사항

- **성능**: 소규모 운영의 메모리·동시 접수 상한을 설정 가능하게 하고 지연되는 외부 요청이 자원을 무기한 보유하지 않게 한다. 미측정 RPS·GPU 처리량을 보장하지 않는다.
- **보안**: 서버 인증·소유권·관리자 검사를 보존하고 로그에 cookie, API key, signed URL, 음성 bytes를 남기지 않는다.
- **정합성**: 티켓 차감·환불·가입 지급은 DB 원장과 일치한다. 외부 실행과 DB 사이 분산 transaction이 없는 사실을 반영해 불명 상태를 복구한다.
- **호환성**: 기존 API의 정상 응답·job identity·asset 관계를 유지한다. additive migration과 구/신 Modal 계약 적용 순서, rollback 제약을 plan에 기록한다.
- **검증**: 경쟁 실행, crash window, timeout, 응답 유실을 가짜 시계·제어된 barrier·격리 DB로 재현한다. 정상 사용자 흐름과 권한 회귀도 검사한다.

## 추가 검증 범위: 브라우저 E2E

사용자가 핵심 사용자 E2E 추가와 변경 전후 비교를 요청했다. 정상 사용자 계약을 변경 전 b333d64와 변경 후 코드에 동일한 브라우저 테스트로 실행한다. ID/시간/외부 URL 등 비결정 값 대신 상태·화면·티켓 수량·소유권을 비교한다. 모든 동작의 100% 동등성을 주장하지 않으며 의도적 장애/제한 정책 차이와 기존 코드의 결함은 구분해 기록한다.

- [x] AC-19: 실제 Next.js HTTP 서버, worker, 격리 PostgreSQL을 거치는 업로드/분석·추천/믹싱·결과 오디오·기록/삭제·실패/환불을 Playwright로 검증한다. 앱 API 응답은 브라우저에서 mock하지 않고 외부 Modal/스토리지만 로컬 테스트 서버로 대체한다.
- [x] AC-20: 서명된 fixture 세션으로 로그인된 화면·로그아웃·비로그인/다른 사용자 접근 차단을 검증한다. 실제 Google 로그인 동의/콜백은 미검증임을 명시한다. 인증 bypass는 끈다.
- [x] AC-21: 같은 E2E 소스로 변경 전후를 실행하고 결과 및 차이를 남긴다. 이후 PR에서 실행할 CI와 로컬 실행 명령을 제공한다. 루트 README는 수정하지 않는다.
