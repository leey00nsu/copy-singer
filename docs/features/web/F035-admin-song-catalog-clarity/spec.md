## 목적

현재 관리자 음원 관리 화면은 사용자 미리듣기와 출처 식별에 쓰는 YouTube 영상, 곡 분석과 AI 믹싱에 쓰는 업로드 파일, 카탈로그 공개 상태를 한 영역에 내부 용어로 섞어 보여준다. 이 때문에 `믹싱 target 음원`, `교체 음원`, `보관`이 각각 무엇을 바꾸는지, 보관 후 데이터가 남는지, 곡을 완전히 삭제할 수 있는지 판단하기 어렵다.

관리자가 각 자료의 역할과 작업 결과를 실행 전에 이해하도록 정보 구조와 용어를 정리한다. 출처·음원 교체는 하나의 안전한 revision 흐름으로 묶고, 보관과 복원은 데이터 삭제가 아닌 추천 노출 관리 작업으로 명확히 제공한다. 참조 이력과 저장 파일의 수명주기를 복잡하게 만드는 영구 삭제 기능은 제공하지 않는다.

## 사용자 스토리

### US-1: 등록 자료의 역할 이해

**As a** 관리자
**I want** YouTube 영상과 업로드 음원 파일이 각각 어디에 쓰이는지 등록 전에 알고 싶다.
**So that** 올바른 영상과 파일을 선택하고 내부 구현 용어를 추측하지 않아도 된다.

**Acceptance Criteria:**

- [ ] 사용자-facing UI에서 `target`을 제거하고 `YouTube 미리듣기 영상`과 `원곡 음원 파일`처럼 실제 역할을 나타내는 일관된 용어를 사용한다.
- [ ] YouTube 영상은 추천 곡의 미리듣기와 출처 식별에 사용된다는 설명을 추가/교체 흐름에서 확인할 수 있다.
- [ ] 원곡 음원 파일은 보컬과 반주가 함께 있는 한 개의 파일이며, 시스템이 보컬을 분리해 음역을 분석하고 전체 원곡에서 원키를 추정한 뒤 같은 원본을 AI 믹싱의 기준 곡과 반주에 사용한다는 설명을 제공한다.
- [ ] 신규 등록은 곡 정보, 미리듣기 영상, 분석·믹싱 파일을 하나의 묶음으로 보여주며 지원 형식과 공개 전 준비 절차를 설명한다.

### US-2: 안전한 출처와 음원 교체

**As a** 관리자
**I want** 기존 곡의 YouTube 영상과 대응 음원 파일을 하나의 교체 작업으로 제출하고 진행 상태를 확인하고 싶다.
**So that** 이전 공개 버전을 실수로 깨뜨리지 않고 새 버전을 준비할 수 있다.

**Acceptance Criteria:**

- [ ] 기본 목록은 현재 공개 버전과 준비 중인 교체 버전을 구분하고, 과거 revision은 보조 이력으로 낮은 위계에 둔다.
- [ ] `영상·원곡 교체`는 새 YouTube URL과 그 영상에 대응하는 원곡 파일 하나를 함께 요구하고, 새 revision을 만든다는 점을 실행 전에 설명한다.
- [ ] 교체 버전이 분석·파일 준비를 모두 마치고 관리자가 공개하기 전까지 현재 공개 버전이 추천과 믹싱에 계속 사용된다.
- [ ] 정상 경로에 중복 노출된 revision별 target 업로드는 제거하고, 원곡 파일 저장 실패를 복구해야 하는 상태에서만 `원곡 파일 다시 업로드` action을 제공한다.
- [ ] 내부 영문 상태는 한국어 상태와 다음 행동으로 표시하며, 공개 불가 action에는 분석 중·파일 누락 등 이유를 함께 제공한다.

### US-3: 공개 중단과 복원

**As a** 관리자
**I want** 곡을 추천에서 내리는 작업의 영향과 되돌리는 방법을 알고 싶다.
**So that** 데이터 삭제로 오해하지 않고 안전하게 카탈로그 노출을 관리할 수 있다.

**Acceptance Criteria:**

- [ ] 기존 보관 action은 `추천에서 제외`로 표시하고, 상태와 filter에서는 `보관됨`·`보관된 곡`을 사용하며 확인 Dialog에서 영향을 설명한다.
- [ ] 공개 중단 즉시 새 추천 집합에서 곡이 제외되고 카탈로그 revision이 갱신되지만, 곡 정보·revision·분석·업로드 파일과 기존 믹싱 결과는 유지된다.
- [ ] 보관된 곡은 상태 filter로 찾을 수 있고, 현재 준비 완료 revision을 `추천에 다시 공개`하는 명시적 복원 action을 제공한다.
- [ ] 복원 조건을 충족하지 못하면 필요한 파일 업로드·분석 재시도·교체 중 다음 행동을 안내한다.

## 기능 요구사항

### FR-1: 관리자-facing 카탈로그 용어

`target`, raw revision status 같은 내부 용어를 기본 UI에서 숨긴다. 화면은 `YouTube 미리듣기 영상`, `원곡 음원 파일`, `현재 공개 버전`, `교체 준비 중`, `보관됨`을 canonical 용어로 사용하고 각 입력과 action 가까이에 실제 역할과 결과를 짧게 설명한다. 원곡 음원 파일은 보컬 단독 파일이 아니라 보컬과 반주가 함께 있는 하나의 원곡 파일임을 명시한다.

### FR-2: 곡 중심 정보 구조

곡 행은 곡 identity, 추천 노출 상태, 현재 공개 버전, 교체 준비 상태와 가능한 다음 action을 먼저 보여준다. revision 이력과 운영 복구 action은 상세 영역에 두고, 새 곡 등록과 기존 곡 교체는 각각 집중된 Dialog 또는 동등한 작업 surface로 제공한다.

### FR-3: 원자적인 교체 준비와 공개

교체 요청은 YouTube URL과 대응 원곡 음원 파일 하나를 한 번에 받아 새 source revision, target asset, 분석 작업을 준비한다. 준비 또는 분석 실패 중에는 기존 active pointer를 유지하고, 준비 완료 후 별도 공개 action에서만 active source·analysis·target을 함께 전환한다. 정상 상태에서는 별도의 두 번째 파일 입력을 제공하지 않는다.

### FR-4: 공개 중단과 복원

보관은 `Song.lifecycleStatus`와 해당 `CatalogEntry.status`를 보관 상태로 바꾸고 공개 집합이 실제로 달라질 때 catalog revision을 한 번 증가시킨다. active pointer, 관련 자료와 기존 믹싱 이력은 유지한다. 복원은 readiness가 유효한 기존 revision을 재공개하는 명시적 서버/UI 계약으로 제공하고 동일 상태의 반복 요청은 revision을 중복 증가시키지 않는다. 관리자 UI와 API에는 곡 aggregate의 영구 삭제 action을 제공하지 않는다.

### FR-5: 상태·확인·접근성

공개, 보관, 복원과 비동기 준비 action은 중복 실행을 막고 결과 toast와 갱신된 상태를 제공한다. 보관은 되돌릴 수 있는 노출 관리 action으로 표현하고, 확인 Dialog에서 추천 제외와 데이터 유지 효과를 함께 설명한다. Dialog title, description, focus와 키보드 동작으로 결과를 색상 이외의 방식으로도 전달한다.

## 비기능 요구사항

- **성능**: 목록 조회에서 삭제 가능 여부와 현재/준비 중 revision을 페이지 단위 bounded query로 계산하며 행별 N+1 요청을 만들지 않는다.
- **보안**: 모든 변경·삭제 API는 서버 관리자 권한, 입력값, 곡 상태와 참조 무결성을 다시 검증한다. 외부 저장소 URL이나 credential은 클라이언트에 노출하지 않는다.
- **내구성**: 보관·복원은 반복 요청에 안전해야 하며 기존 active revision, 저장 파일과 믹싱 이력을 보존한다.
- **접근성**: 최소 360px mobile부터 desktop까지 action과 상태가 겹치지 않고, 입력 label·상태 설명·Dialog 확인을 키보드와 보조 기술로 사용할 수 있어야 한다.
